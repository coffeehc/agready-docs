Install and start AgReady

Install AgReady on the machine that will host your instance, start its server, and open that instance in your browser. The AgReady website is documentation—not a hosted account or your running instance.

This guide covers the v0.0.1 release and its associated installer defaults. The download entrypoint and platform modules can change independently. Review the installer you actually download. These instructions are based on release materials, not a claim that a clean installation was tested here.

Choose your download

These are the four verified AgReady Server v0.0.1 archives, published October 26, 2026. They include the Web UI. Check the latest GitHub release for newer versions before choosing; the links below stay pinned to v0.0.1.

  • macOS · Apple silicon: Download macOS ARM64 (.tar.gz) — darwin-arm64.
  • macOS · Intel: Download macOS Intel / AMD64 (.tar.gz) — darwin-amd64.
  • Linux · Intel or AMD 64-bit (x86-64): Download Linux AMD64 (.tar.gz) — linux-amd64.
  • Linux · ARM 64-bit: Download Linux ARM64 (.tar.gz) — linux-arm64.

darwin means macOS in these filenames; amd64 also covers compatible Intel x86-64 machines. This release does not include a native Windows archive.

On a Mac, use Apple menu → About This Mac: an Apple chip means Apple silicon; an Intel processor means Intel. On Linux, the read-only command uname -m reports the current architecture: x86_64 maps to AMD64 and aarch64 to ARM64. For a remote installation, check the target server, not the computer running your browser. If the result differs, verify compatibility rather than guessing.

Before using a package, read the LICENSE and EULA. Compare the downloaded archive with its exact filename in SHA256SUMS; do not use the binary checksum list for an archive. Use the checksum steps below, then see the manual example for Linux AMD64 or read your package’s bundled instructions for its platform. Downloading or extracting a package does not install a service or configure a model.

Prefer the installer? Follow the download-and-review steps below instead. Runtime Assets and tool plugins remain separate from the Server.

Installer or manual archive: keep the release sources separate

The installer and the manual links above are two different ways to obtain AgReady Server. Do not assume they select the same version just because they appear on this page.

  • Version-pinned manual archive: the four GitHub links above select v0.0.1 explicitly. The GitHub latest-release page describes that repository's releases, not the current version selected by the download-host installer.
  • Catalog-driven installer: the installer source reads the Server version from the download host's version catalog. The script and its platform modules can change separately from these pinned links. Review the downloaded script, the selected version and that release's instructions before execution.

If the two sources show different versions, first decide which release you intend to install. A newer version recorded in a source repository is not proof that its public packages are available. This guide does not certify the current download-host version or promise that the GitHub mirror has every release.

Keep each package with its own release metadata and checksums:

  1. Match the version, operating system and architecture in the archive filename to the release you selected.
  2. Get SHA256SUMS from that same release and find the exact archive filename. Do not reuse the v0.0.1 list for a different version or substitute a similarly named package.
  3. Use the archive verification steps before extraction. A catalog field named binary_sha256 describes the unpacked executable, not the compressed archive; BINARY_SHA256SUMS is also not the archive checksum list.
  4. If the package or its matching checksum list cannot be retrieved, or the digest differs, stop before extraction or execution. Preserve the error and chosen release details for the administrator rather than bypassing the check.

After installation, check the running Server's reported version and follow the startup checks below. Opening a download link, saving a file or finishing a checksum check does not establish that the Server is installed or ready for a task.

Verify your downloaded archive

Before extracting or running a manually downloaded package, check that its bytes match the checksum published for that release. Save the archive and its matching release checksum list (the examples here use v0.0.1 SHA256SUMS) in a folder you can inspect. Open a terminal in that folder; the commands below only read the archive and print its SHA-256 digest.

macOS example, Apple silicon:

shasum -a 256 ./agready-v0.0.1-darwin-arm64.tar.gz

For an Intel Mac, use agready-v0.0.1-darwin-amd64.tar.gz instead.

Linux example, Intel or AMD x86-64:

sha256sum ./agready-v0.0.1-linux-amd64.tar.gz

For Linux ARM64, use agready-v0.0.1-linux-arm64.tar.gz instead. These examples are pinned to v0.0.1; a newer archive needs the checksum list from its own release.

  1. Open SHA256SUMS as text and find the line with the exact archive filename. The published list prefixes archive names with ./, which means the current folder.
  2. Compare the complete 64-character digest, not just its first or last characters, with the terminal output.
  3. If the digest matches, continue with the Linux AMD64 manual example or your package’s bundled instructions. This checks the download, not whether installation, startup or a model connection will work.

If the file is missing, check the folder and actual filename. If the digest differs, do not extract or run the archive: confirm you selected the correct release and platform, download again from the official release, and recheck. If it still differs, stop and report the version, filename and mismatch without credentials or private configuration.

Do not use BINARY_SHA256SUMS to check a .tar.gz archive. A matching digest is not a digital signature or an independent guarantee that the publisher is trustworthy, and it does not grant a license.

Before installing

  • Choose Linux or macOS, then the matching amd64 or arm64 package. Do not choose by operating system alone.
  • Read the release notes, LICENSE and EULA. A public download does not grant an open-source license.
  • Decide which machine will store the instance's configuration and data. On a remote server, arrange an administrator-approved access method before opening the UI.
  • Keep the provider credentials you intend to use available privately. Do not put them in a support message or shell command copied into public logs.

The release includes Server archives with the Web UI. Runtime Assets and tool plugins are separate; installing the Server does not prove tools are ready.

Use the v0.0.1 archive manually on Linux AMD64

Use this example only for the v0.0.1 Linux AMD64 (x86-64) archive. If you want this exact release, do not run the catalog-driven installer instead. For macOS or Linux ARM64, consult the instructions in the archive for that platform rather than reusing the commands below.

After the archive checksum matches, open a terminal in the folder with the download. Extract into a new, writable directory so these steps do not write into an existing instance:

mkdir agready-manual-v0.0.1 &&
  tar -xzf ./agready-v0.0.1-linux-amd64.tar.gz -C agready-manual-v0.0.1 &&
  cd agready-manual-v0.0.1/agready-v0.0.1-linux-amd64

Continue only if all three commands succeed. Stay in the extracted directory and read the bundled README.md, LICENSE and EULA.md. If you are authorized to use this release, check the executable:

./agready version

The verified Linux AMD64 executable reports Version:0.0.1 and GitTag:v0.0.1. That confirms the reported version, not whether the service is running.

The bundled README gives this start command, also run from the extracted directory:

./agready start

This manual path does not set up the installer’s managed systemd service. The executable uses ./config.yml by default. In an isolated Linux test without a stable device identifier, it created a configuration file but stopped before serving the Web UI. If startup fails, consult the terminal error and ask your administrator or support rather than changing the device identifier or bypassing license checks.

Only after the server starts and the Web UI opens at your administrator-approved address, continue to initial setup and the first task. Extraction and a successful version check are not a readiness check.

Download and review the installer

Download without executing:

curl -fsSL https://download.agready.ai/agready/install.sh -o install-agready.sh

Inspect the saved script and the platform modules it retrieves. Confirm its destinations and requested privileges before running it:

bash install-agready.sh

The platform start steps below cover the installer path. If you downloaded the pinned archive instead, use the manual Linux AMD64 example or the instructions bundled for your platform.

Start on Linux

The default installation puts the executable at /usr/local/bin/agready and uses /opt/agready/server as the server working directory. The installer uses elevated privileges where needed, creates a systemd service named agready-server, enables and restarts it, and checks readiness.

Inspect the final installer output. To investigate without restarting:

systemctl status agready-server --no-pager
journalctl -u agready-server -n 100 --no-pager

Access to service details and journals depends on your permissions. If the unit is missing or access is denied, ask the administrator to inspect the installation rather than changing permissions or rerunning setup blindly.

Start on macOS

The macOS installer does not automatically activate a managed service. For a fresh installation using the default paths, the printed start command is equivalent to:

cd "$HOME/.local/share/agready/server" && "$HOME/.local/bin/agready" start

Use the actual command printed by your installer if you selected different paths or it found an existing executable. Inspect the terminal output to determine whether startup succeeded.

Open your instance

The Linux installer defaults to checking http://127.0.0.1:18888/ for readiness. This is a local check, not a statement that the server listens only on loopback. In a browser on the same machine, that address refers to that machine. On your laptop, it does not refer to a remote server.

For a remote instance, use the address or secure connection method approved by its administrator. Do not disable certificate checks or authentication, or open a public port merely to make the page load. Do not infer a macOS address from a Linux readiness check; confirm your actual startup configuration.

Confirm the next step

A successful download is not a running service. A running service is not yet a configured model. Once the instance opens, follow Get started to initialize it, then test a real model connection and run the small text-only task.

If a login screen appears instead of first-time setup, do not initialize the instance again. Ask its administrator for access. For other failures, use the diagnostic checks.
