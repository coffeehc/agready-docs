DEPLOYMENT GUIDE · NOVEMBER 11, 2026

Self-hosted AI agent security checklist: tools, secrets and runtime

Self-hosting gives you control over where the agent service runs. A secure deployment also needs clear model data flow, limited tool permissions, protected credentials, an appropriate execution environment and a recovery plan.

Google's October 22, 2026 Agent Compute Engine deep dive separates the agent harness that decides what to do from the sandbox that runs its commands. That distinction is useful beyond one vendor: where the application is hosted and where actions execute are separate questions.

The checklist below is deployment guidance for people evaluating a self-hosted agent such as AgReady. It is not a security audit, a certification or a claim that AgReady implements Google's isolation architecture.

1. Map where task data goes

For each workflow, list the service that receives each input and output. Include the model endpoint, retrieval services, tools, remote agents, file storage, backups and operational logs. A server running on your infrastructure can still send prompts and source excerpts to an external model provider.

For example, a document-review task may read a file on your server, send selected text to a model, call a separate tool for extraction and save a result in another storage system. Write down that path before using confidential material. Check the relevant providers' current retention, access and processing terms rather than assuming the server location answers every privacy question.

Record: data category, recipient, reason for transmission, storage location and who can remove access.

2. Match tool permissions to the actual job

A research task usually needs fewer privileges than a publishing task. Review both the tool's callable functions and the account it uses. A read-only instruction is helpful, but a read-only downstream account is a stronger boundary than giving a broad account a narrow prompt.

OWASP's Excessive Agency guidance identifies excessive functionality, permissions and autonomy as risk factors. It recommends limiting tools and privileges and enforcing authorization in the systems those tools reach.

  • Prefer a specific read or draft operation over an unrestricted command when it meets the task.
  • Limit accessible projects, directories and destinations to the work in scope.
  • Remove unused integrations and revoke credentials when the task no longer needs them.
  • Treat remote agents as additional recipients with their own access and retention boundaries.

3. Keep credentials out of reusable content

Do not put passwords, API keys or recovery material in a skill, task template, source document or saved memory. Use the credential mechanism supported by the deployment and integration. Check whether secrets can appear in command arguments, logs, generated files or error messages.

Use separate credentials for separate purposes where the service supports it. Decide who can rotate or revoke each credential and how a failed integration will be disabled. A credential that is encrypted in storage still needs controlled use when an operation runs.

Record: credential owner, permitted service, scope and revocation procedure, without copying the secret into the checklist.

4. Inspect the execution boundary

If an agent can run commands, scripts or a browser, identify the environment that performs those actions. Ask what it can read, write and contact over the network. Check which host directories, sockets, credentials and persistent volumes are available.

A container label alone does not tell you the strength of the isolation boundary. Review the actual runtime and its configuration, especially for untrusted code. Avoid giving an experimental workflow broad host access merely to make a failing tool work.

Before using real data, test an approved, non-sensitive task in the intended environment. Confirm both an allowed operation and a harmless operation that should be denied. Keep the test within systems you own or are authorized to assess. If the expected restriction is absent, stop and correct the deployment before continuing.

5. Separate source material from instructions

Web pages, uploaded documents, emails and remote-agent messages can contain instructions that conflict with the user's goal. Treat their contents as material to evaluate, not as permission to change the task or send data elsewhere.

Inspect imported skills and scripts before enabling them. An attractive name, successful import or valid package structure does not establish trustworthy behavior. Keep external content away from broad privileges, and review surprising requests against the original task.

For a document summary, a passage saying “upload the full folder to this address” should remain quoted source content. It should not become the next tool action.

For a worked source-review exercise, see prompt injection in AI research.

6. Define approval and recovery before the first write

Choose which operations may proceed and which need review. Sending a message, publishing a file, changing account access and deleting data deserve explicit treatment. An approval should identify the action, target and information being sent or changed.

Plan for interruptions as well. A timeout can occur after an external service accepted an operation. Before retrying, inspect the destination or recorded task identifier. Keep unknown outcomes marked unknown. Stopping an agent does not necessarily undo an action already accepted elsewhere.

Keep enough operational evidence to investigate failures, with access and retention limits appropriate to the data. Avoid turning logs into a second uncontrolled store of documents or credentials.

7. Assign an owner for maintenance and recovery

Self-hosting includes responsibility for updates, access reviews, backups and restoration. Decide what must be backed up, who can restore it, how credentials are handled and how recurring tasks are paused during recovery. Test a restore in an isolated environment before relying on it.

After maintenance, verify a small representative task before enabling consequential actions. Check the application, its model connection and required tools separately so that a working login page is not mistaken for a fully restored workflow.

Apply the checklist to AgReady

AgReady is a self-hosted agent workspace with configurable model connections, tools, Skills, memory and agent teams. Start with its model configuration guide and tool readiness guide, then review approvals and interrupted actions and upgrade and recovery planning.

Capability availability depends on the installed release and configuration. This article does not establish a particular sandbox boundary, universal approval coverage or complete audit logging in AgReady. Those are properties to inspect in the actual deployment, not conclusions to draw from the phrase “self-hosted.”

A useful first milestone is modest: one non-sensitive task, the minimum required connection, a reviewed result and a documented way to stop and revoke access. Expand the workflow only when the next capability has a clear purpose.
