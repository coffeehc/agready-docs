Work with an AI agent team in AgReady

An agent team brings a manager and specialist agents together around a goal. Create a team, give its manager a bounded brief, and use the fictional documentation review below to check whether its reports support the final answer.

Reviewed October 28, 2026

This guide describes the current development interface; labels and availability may differ in other versions. The creation form was checked without creating a team. Team execution, archive and restore behavior were reviewed from product documentation and implementation, not exercised in this check.

When to use an agent team

An agent team is useful when a goal involves several specialties and someone needs to coordinate the work. In AgReady, you work with a team manager, who can recruit specialist agents, assign work, review their reports, and bring the results together.

Start with a normal session for a straightforward task. Use a team when coordination adds value, not simply to increase the number of agents. For example, separate reviews of setup instructions and a first-use example may reveal different problems, while the manager combines them into one prioritized result.

A team is not automatically faster, cheaper or more accurate than one agent. Compare the usefulness of the result, the work required to review it, and any model or tool usage your setup makes visible. Multiple reports repeating the same source are not independent confirmation.

Create the team

  1. Select New team in the session sidebar.
  2. Enter a Team name.
  3. Describe its ongoing Team responsibilities.
  4. Select Create agent team and wait for initialization.
  5. Open View manager session when the team is ready.

Responsibilities describe what the team is for. They are not a substitute for a specific first task or permission to take every possible business action.

Give the manager a bounded first goal

Describe the outcome, available materials, allowed actions, and how you will judge the result. For example:

Review these product documentation pages and identify up to three important gaps for a first-time user. Use only the supplied pages. Return evidence links and suggested outlines. Do not publish changes, contact anyone, or create recurring tasks.

This is an instruction example, not a claim that the task has been tested successfully.

The manager may propose a first pilot or ask for a missing decision. Specialist agents are recruited as needed; creating a team does not require filling every possible role in advance.

Try a source-based documentation review

This small exercise uses fictional documentation for an imaginary project called Harbor. It is a reference exercise, not an executed AgReady team run, a product feature claim or a performance comparison. It intentionally needs no web access, private files or external changes. For such a small packet, one session may be sufficient; use it with a team only if you want to examine how the manager coordinates and reconciles work.

1. Supply the complete source packet

Keep the source labels when copying these excerpts into the manager session. They let you trace a proposed fix back to the material that supports it.

  • [H1] Harbor start page: “New here? Follow the Setup page, then complete the First task.” No prerequisites are listed on the start page.
  • [H2] Harbor setup page: “Before using any example, install the image-reader extension. The extension is needed to extract text from scanned images.”
  • [H3] Harbor first-task page: “In a configured text session, paste the meeting notes below and ask for three action items. This example uses pasted text only.” The page does not explain how to configure a text session.
  • [H4] Harbor maintainer note: “The image-reader extension is not required for the pasted-text first task. We have not published revised setup instructions.”

2. Give the manager a review-only brief

The suggested review roles below are task instructions, not built-in role names or a promise about how many specialists the manager will recruit.

Review only Harbor sources H1–H4 above for a first-time reader. Inspect prerequisites and the first-task path separately, using specialist help only where useful. Have each review cite source labels and separate an observed gap from a suggested fix. Reconcile the reviews into at most three prioritized gaps, each with evidence, reader impact, a draft wording change and any unresolved question. Do not invent missing setup steps. Do not browse, install anything, change files, publish, contact anyone or schedule work. If reports disagree, show the disagreement and the source that resolves it, or leave it unresolved. Stop after delivering the review in this conversation.

3. Compare the delivery with this reference

Wording and priority can differ. A grounded answer should identify the following issues without claiming that any correction has already been published:

  1. The extension requirement is too broad. H2 says it applies to every example, while H3 describes pasted text and H4 explicitly says that task does not require it. A suggested revision is: “The image-reader extension is required for scanned-image extraction, but not for the pasted-text first task.” That is proposed copy for the fictional pages, not an AgReady installation instruction.
  2. Text-session preparation is missing from the packet. H3 requires a configured session but supplies no steps, and H1 only points readers onward. Suggest adding a link to verified text-session setup instructions. The correct steps and link remain unknown; the team should request them rather than invent a URL, command or supported provider.

H4 also establishes a status boundary: the maintainer has clarified the requirement, but revised setup instructions are not published. The final review should preserve that distinction. “At most three” is a limit, not a reason to manufacture a third independent finding.

Acceptance check: can you find the supporting excerpt for each finding, distinguish the proposed wording from a completed edit, and see what is still unknown? If not, ask the manager to revise the result before expanding the task.

Inspect progress and results

Open the team information panel to see its organization status, manager, active member count, and goals. Team chat shows collaboration records, including assignments, reports, and deliveries.

  • Ready describes the team’s organization, not a completed goal.
  • A member report is material for the manager to review.
  • Delivered by manager records the manager’s delivery; inspect the actual result before accepting it as correct.

Read the final delivery alongside the relevant member reports. If two reports disagree, ask the manager to identify the specific conflicting statements, compare their evidence and carry forward anything unresolved. A majority of agents agreeing is not a substitute for a supporting source. Avoid requesting another full round when one narrow clarification would resolve the issue.

Teams use the models, tools, Skills, and workspace access available to their sessions. A role description does not grant additional access. If an action requires your approval, review that original request rather than treating the team’s goal as blanket permission.

Change direction or stop work

Tell the manager clearly when you want to revise, pause, resume, or cancel a specific goal. Check the resulting goal status and the manager’s explanation. A user-requested pause should remain in effect until you authorize resuming.

To stop the team as an organization while preserving its records, use Archive team. Restore team is available for an archived team. Stopping an individual session run is not the same as archiving the entire team.

If something goes wrong

If creation reports an error, use Retry creation with the original details instead of repeatedly creating new teams. If work is blocked, ask the manager for the affected goal, evidence collected, attempted approaches, and the exact decision or access required.

  • The team is ready but no useful result appears: check that you gave the manager a specific goal after creation. Request the current goal state, last completed step and exact blocker; do not create duplicate teams just to restart the same work.
  • Reports repeat each other: ask the manager to narrow overlapping assignments and explain what each review adds. More specialists are not automatically the next step.
  • The delivery lacks evidence: request source labels or links for the affected findings and mark unsupported conclusions as unverified. Do not treat a polished summary as proof that a source was read.
  • A tool or action is unavailable: identify the exact missing access or approval. Team membership does not resolve a model connection problem or grant tool permissions. Follow tool readiness checks before expanding access.

Assess the team by useful, verified deliverables, not by how many members it created or how much conversation it produced. If the task no longer benefits from separate reviews, use a reviewed handover brief for a single session and separately pause or cancel the original team goal to avoid overlapping work.
